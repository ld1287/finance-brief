## 1. 用户提出的 4 个概念问题（先回答清楚）

### 1.1 「你为何要这样设计文件层级？」

`apps/desktop/` 镜像 `Octoscript-Makepad/apps/flutter-samples/` 的 3 文件布局（main.rs + lib.rs + datasources.rs）：
- `main.rs`（8 行）：`fn main() { finance_brief::app_main() }` —— 仿 flutter-samples 的入口
- `lib.rs`：BAKED 拼接常量 + `App` struct + `script_mod!` + `AppMain` 实现
- `datasources.rs`：把 `host.fetch("cap.X", args)` 桥到 9 个 native adapter

这是 Octoscript-Makepad 官方推荐的「cdylib for mobile + rlib for desktop」最小形态（`Cargo.toml:22-29` `crate-type = ["cdylib", "rlib"]`）。

**但用户觉得「好多实现都是空的」是合理的批评**：3 文件全塞到一个 `datasources.rs` 里，18 个 stub 横向展开，没有按 MVP-TODO.md §4「关注点」列拆模块。

### 1.2 「不要在子文件夹里与项目同名的文件夹」

原 `apps/finance-brief/finance-brief/`（crate 名 = 父目录名 = 项目名）是反模式 —— 路径 `apps/finance-brief/finance-brief/Cargo.toml` 自指了三层。

commit `2ba0759` 已经 `git mv apps/finance-brief apps/desktop`：
- 目录名 = `desktop`（桌面端入口的职责命名）
- crate name = `finance-brief`（保持发布标识稳定）
- bin name = `finance-brief`（`cargo run -p finance-brief --release`）

这样三方解耦，避免自指。Octoscript-Makepad 本身也是 `apps/flutter-samples/`（不是 `apps/flutter-samples/flutter-samples/`）。

### 1.3 「apps/desktop 的功能是干什么的，不能集成到 native 里吗？」

**不能，且不应该**。两者职责正交：

| 维度 | `apps/desktop/` | `native/` |
|------|----------------|-----------|
| 类型 | binary + cdylib + rlib | rlib-only |
| 入口 | `fn main()` 开窗口 | 无 |
| 依赖 | makepad-widgets / makepad-plot / octoscript-* | reqwest / serde_json / tokio / chrono |
| 职责 | VM 挂载 + Octoscript 评估 + Splash.view + AppMain | fetch + parse + cache + JSON Schema 校验 |
| 测试 | 0 测试（GUI context） | 65 PASS（pure data） |
| Phase 4 (OctoSense shell) | dlopen 这个 cdylib | 不直接被 shell 用 |

如果合并：
- `native/` 的 HTTP 客户端会被 `cargo makepad ohos deveco` 编进 HAP native lib（多 2-3 MB 无用代码）
- 65 个 `native/` 测试要么改 GUI test harness，要么跑不起来
- `SplashVm` 桩类型与真 makepad `ScriptVm` 在同一 crate —— 命名冲突风险
- `native/` 给 CLI / server / future card 复用的可能性消失

**flutter-samples 也是同样分法**：`Octoscript-Makepad/apps/flutter-samples/` 是 binary，`Octoscript-Makepad/crates/octoscript-*-render/` 是 library。

### 1.4 「集成了就不能使用 octosence-app-hub 上运行到 OctoSense 了？」

**技术上不会**。OctoSense shell 启动 app 的方式是 `dlopen("libfinance_brief.so")`（Android HAP）或 `exec("finance-brief")`（desktop launcher），它不感知 Rust crate 拓扑。

但**架构上不应该**：
- Phase 4 `OctoScript#56` 修好后，shell 会以 `cdylib` 形式 dlopen `apps/desktop`（需要 `AppMain for App` 暴露 `app_main()`）
- mobile cdylib 与 desktop binary 共用 `lib.rs`（per `main.rs:1-7` 注释）
- 如果 `native/` 跟 `apps/desktop/` 合并，mobile cdylib 会带 HTTP client —— 移动端启动慢、内存 footprint 大，且违反最小依赖原则
- `native/` 应保持 library-only，让 shell 在 host 层做 capability 注入（更利于沙箱化）
